# 一、CUDA 源文件
## 1. include
```c
#include <cuda_runtime.h>
#include <stdio.h>
```
## 2. CUDA算子
```c
__global__ void add_kernel(float *a, float *b, float *c, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        c[idx] = a[idx] + b[idx];
    }
}
```

## 3. 调用函数
```c
extern "C" __declspec(dllexport) 
void launch_add(float *a, float *b, float *c, int n) {
    float *d_a, *d_b, *d_c;
    size_t bytes = n * sizeof(float);

    cudaMalloc(&d_a, bytes);
    cudaMalloc(&d_b, bytes);
    cudaMalloc(&d_c, bytes);

    cudaMemcpy(d_a, a, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_b, b, bytes, cudaMemcpyHostToDevice);

    int threads = 256;
    int blocks = (n + threads - 1) / threads;
    add_kernel<<<blocks, threads>>>(d_a, d_b, d_c, n);

    cudaMemcpy(c, d_c, bytes, cudaMemcpyDeviceToHost);

    cudaFree(d_a);
    cudaFree(d_b);
    cudaFree(d_c);

    cudaError_t err = cudaDeviceSynchronize();
    if (err != cudaSuccess) {
        printf("CUDA Error: %s\n", cudaGetErrorString(err));
    }
}
```

# 二、编译
## Windows
```bash
nvcc -shared -o vector_add.dll vector_add.cu -Xcompiler "/EHsc /W3 /nologo /O2 /FS"
```
| 参数 | 全称/含义 | 作用 |
|------|-----------|------|
| `/EHsc` | Exception Handling, C++ style | 启用 C++ 异常处理。`s` 表示假定 `extern "C"` 函数不会抛异常，`c` 表示只捕获 C++ 异常。**如果没有这个选项，使用 `try/catch` 或标准库会报错。** |
| `/W3` | Warning level 3 | 设置警告级别为 3（默认是 `/W1`）。级别越高，警告越严格。`/W3` 是常用的“中等偏严”级别，`/W4` 更严格。 |
| `/nologo` | No logo | 编译时不打印版权横幅，让输出更干净。 |
| `/O2` | Optimize level 2 | 启用速度优化（级别 2）。这是发布版本的常用优化等级，会做内联、循环优化等。 |
| `/FS` | Force Synchronous PDB writes | 强制串行写入 PDB 调试文件。**当多个 `cl.exe` 进程并发写入同一个 PDB 时会用到**，`nvcc` 内部可能会并行调用编译器，所以加上它避免冲突。 |


## Linux/macOs
```bash
nvcc -shared -Xcompiler -fPIC vector_add.cu -o vector_add.so
```
这里 `-fPIC` 就是传给 `g++` 的参数（生成位置无关代码，共享库必需）

# 三、运行
## 1. import
```py
import ctypes
import numpy as np
import os
```

## 2. 加载库并设置签名
```py
# 加载库
lib_path = './code/cuda/so/libvector_add.so' if os.name != 'nt' else './code/cuda/dll/vector_add.dll'
lib = ctypes.cdll.LoadLibrary(lib_path)

# 设置函数签名
lib.launch_add.argtypes = [
    ctypes.POINTER(ctypes.c_float),
    ctypes.POINTER(ctypes.c_float),
    ctypes.POINTER(ctypes.c_float),
    ctypes.c_int
]
lib.launch_add.restype = None
```

## 3. 调用
```py
# 准备数据
n = 1000000
a = np.random.randn(n).astype(np.float32)
b = np.random.randn(n).astype(np.float32)
c = np.zeros_like(a)

# 调用
lib.launch_add(
    a.ctypes.data_as(ctypes.POINTER(ctypes.c_float)),
    b.ctypes.data_as(ctypes.POINTER(ctypes.c_float)),
    c.ctypes.data_as(ctypes.POINTER(ctypes.c_float)),
    n
)

# 验证
print(c)
print(a+b)
print("Max difference:", np.max(np.abs(c - (a + b))))
```

# 五、基础算子一览

约定：**指针参数在前，标量参数在后**；所有输入/输出均为一维连续 `float32` 数组，长度 `n`。

| 源文件 | 导出函数 | 运算 |
|--------|----------|------|
| `vector_add.cu` | `launch_add(a, b, c, n)` | $c = a + b$ |
| `vector_sub.cu` | `launch_sub(a, b, c, n)` | $c = a - b$ |
| `vector_mul.cu` | `launch_mul(a, b, c, n)` | $c = a \times b$ |
| `vector_div.cu` | `launch_div(a, b, c, n)` | $c = a \div b$ |
| `vector_neg.cu` | `launch_neg(a, c, n)` | $c = -a$ |
| `vector_scale.cu` | `launch_scale(a, c, alpha, n)` | $c = a \times \alpha$ |
| `vector_add_scalar.cu` | `launch_add_scalar(a, c, beta, n)` | $c = a + \beta$ |
| `axpy.cu` | `launch_axpy(x, y, alpha, n)` | $y = \alpha x + y$（原地更新） |
| `vector_relu.cu` | `launch_relu(a, c, n)` | $c = \max(a, 0)$ |
| `vector_maximum.cu` | `launch_maximum(a, b, c, n)` | $c = \max(a, b)$ |
| `vector_minimum.cu` | `launch_minimum(a, b, c, n)` | $c = \min(a, b)$ |
| `vector_sum.cu` | `float launch_sum(a, n)` | 归约求和 |
| `vector_dot.cu` | `float launch_dot(a, b, n)` | 归约点积 |

## 归约算子说明

`vector_sum` / `vector_dot` 采用**两阶段归约**，返回值即计算结果：

1. 每个线程读一个元素（越界补 0）；
2. 块内用 `extern __shared__` 动态共享内存做折半（tree）归约；
3. 每个块只由 `tid == 0` 执行一次 `atomicAdd` 写入全局累加器，避免大量原子竞争。

对应 Python 侧需设置返回值类型：

```py
lib = ctypes.CDLL('./code/cuda/dll/vector_sum.dll')
lib.launch_sum.argtypes = [ctypes.POINTER(ctypes.c_float), ctypes.c_int]
lib.launch_sum.restype = ctypes.c_float

total = lib.launch_sum(a.ctypes.data_as(ctypes.POINTER(ctypes.c_float)), n)
```

# 六、性能对比（CUDA 算子 vs EnNeuro CPU / GPU）

```bash
python code/tests/bench_cu_vs_eneuro.py
python code/tests/bench_cu_vs_eneuro.py --sizes 100000,1000000,10000000 --iters 20 --rounds 7 --csv bench.csv
```

对比三方：

| 被测对象 | 说明 |
|----------|------|
| `CUDA(dll)` | 本目录编译出的算子；每次调用含 `cudaMalloc/cudaFree + H2D + kernel + D2H` |
| `CPU(EnNeuro)` | `eneuro.base.Tensor` + numpy 后端（含自动微分图的构建开销） |
| `GPU(EnNeuro)` | `eneuro.base.Tensor` + cupy 后端，数据常驻显存、不计拷贝 |

> 测量方法：先统一 warmup，再把「所有算子 × 所有后端」放进同一个队列做 **round-robin 交错测量**，
> 取多轮中每轮平均耗时最小值。若改成「把一个算子连续测一长串再换下一个」，实测会引入约 2 倍的
> 位置/温度漂移，结论会完全失真。

实测环境：RTX 4060 Laptop / CUDA 12.6 / cupy 14.0.1 / numpy 2.4.6，单位 ms。

| n | 算子 | CUDA(dll) | CPU | GPU | CUDA 耗时 ≈ 拷贝字节 / 5GB/s |
|---|------|-----------|-----|-----|------|
| 1e5 | add | 0.5045 | 0.0166 | 0.0150 | 3 次拷贝 |
| 1e5 | neg | 0.4336 | 0.0135 | 0.0142 | 2 次拷贝 |
| 1e5 | sum | 0.3477 | 0.0196 | 0.0192 | 1 次拷贝 |
| 1e6 | add | 2.387 | 1.005 | 0.0215 | 3 次拷贝 |
| 1e6 | neg | 1.617 | 0.9352 | 0.0195 | 2 次拷贝 |
| 1e6 | sum | 0.8717 | 0.1530 | 0.0204 | 1 次拷贝 |
| 1e7 | add | 18.69 | 10.37 | 0.5454 | 3 次拷贝 |
| 1e7 | sum | 6.587 | 3.465 | 0.2112 | 1 次拷贝 |
| — | 传输基线(H2D+D2H) | — | — | 0.154 / 1.643 / 15.85 | 2 次拷贝 |

## 结论

1. **当前 `CUDA(dll)` 是「拷贝受限」而非「算力受限」**：耗时 ≈ 传输字节数 ÷ 约 5 GB/s（PCIe 实测带宽）
   ＋ 约 0.25 ms 固定开销（`cudaMalloc/cudaFree` + kernel 启动 + 同步）。
   同一算子的耗时严格正比于拷贝次数：3 次拷贝（add/sub/mul/div/max/min/dot）> 2 次（neg/relu/scale）
   > 1 次（sum），与 n 无关。
2. 因此在这个朴素实现下，**CUDA(dll) 在 1e5 ~ 1e7 全部规模上都慢于 CPU numpy**
   （CPU/CUDA 比值 0.03x ~ 0.6x），比 cupy 常驻显存方案慢 30 ~ 100 倍。
3. 但 **kernel 本身极快**：n = 1e6 时 GPU 0.02 ms vs CPU 1.0 ms（≈ 50x），
   瓶颈完全在主机与设备之间的数据搬运。
4. 有个例外：`scale` / `add_scalar` / `axpy` 这类算子 CUDA(dll) 反而**快于 CPU 1.2 ~ 2.4 倍**——
   因为 EnNeuro 的 CPU 路径要为标量运算构建自动微分图（`Tensor + 标量` 会额外创建 Tensor）。
5. 优化方向：把接口从「每次调用都用主机指针」改为**显存常驻**（一次 `cudaMemcpy` 入，多次 kernel，
   最后一次拷回），或直接复用 cupy 的显存指针（`cupy.ndarray.data.ptr` + `__cuda_array_interface__`），
   这样 CUDA 算子才能真正体现算力优势。

   这是一个设计权衡问题，其中"cupy 指针能否直接被 nvcc 编译的算子使用"是决定性的未知项。我先做个小实验把它验证掉，再给对比。

# 七、优化方案对比
- **A. 自管理显存常驻**：算子库自己 `cudaMalloc` 一块常驻 buffer（最好带池），暴露 `upload / download / *_dev` 三段式 API。
- **B. 复用 cupy `data.ptr`**：算子库**不分配任何显存**，只接受别人给的设备指针；内存由 cupy 拥有。

B 本质上是 A 把「内存归属」这一层让出去之后的极简形态，二者可以叠加（B 用 cupy 分配 workspace）。

## 对比

| 维度 | A. 自管理显存常驻 | B. 复用 cupy `data.ptr` |
|---|---|---|
| 显存归属 | 算子库，需 `cudaFree` 或自建池 | cupy，靠 Python 引用计数 |
| 接入成本 | 每个算子 + 分配/释放/池/生命周期 API | 每个算子只加一个 `*_dev` 导出，上层传 `.data.ptr` |
| **数据本来就在 cupy 时** | **仍需一次 D2D 搬运**（~200–400 GB/s，比 PCIe 快但仍非零） | **零拷贝** |
| 数据一致性 | 可能出现「显存副本」与「cupy 数组」两份不一致 | 天然唯一副本 |
| 分配开销 | 自建池，否则 ~0.25 ms/次的 `cudaMalloc` 开销会回来 | 直接复用 cupy 成熟的池（含 async allocator） |
| 流 / 异步 | 自己管流、事件、同步 | 透传 `get_current_stream().ptr` 即天然有序 |
| 多设备 | 自己 `cudaSetDevice`，易踩「设备不匹配」 | cupy 已处理，仍须校验同卡 |
| **不装 cupy 的环境** | ✅ 可用 | ❌ 强依赖 |
| 生态互操作 | 要自己实现 `__cuda_array_interface__` 才能被复用 | ✅ 天然融入 torch / numba / pycuda 生态 |
| 内存布局控制 | 完全可控（对齐、tiling、融合 workspace） | 借 cupy 分配，够用但控制力稍弱 |
| 主要风险 | 泄漏、双重释放、池碎片、设备不匹配 | **生命周期悬垂**（异步未同步时数组被 GC） |
| 代码量 | 大 | 小 |

## 决定性的几个技术细节

1. **必须同一个 primary context**。我们已实测共享，但前提是**同一张卡**。多卡时 `cupy` 切了 device 而 kernel 还在默认 device 上跑，会直接报 `invalid device pointer` 或写错内存。
2. **stream 一定要透传**。cupy 在非默认流里操作时，如果我们仍在 null stream 上启动，两者无序 → 读到旧数据。签名建议：
   ```c
   void launch_add_dev(const float *a, const float *b, float *c, int n, void *stream);
   // kernel<<<blocks, threads, 0, (cudaStream_t)stream>>>
   ```
   用 `void*` 收 `cp.cuda.get_current_stream().ptr`，Python 侧最省事。
3. **`data.ptr` 只对 float32 + C 连续成立**。非连续数组必须先 `ascontiguousarray`——那是**隐式拷贝**，会悄悄吃掉收益。建议在 Python 侧做一次校验（最好缓存校验结果，别放进热路径）。
4. **反向包装必须保活 owner**：`cp.cuda.UnownedMemory(ptr, size, owner)` 的 `owner` 要负责释放，`owner=None` 就得自己保证在 cupy 数组销毁前不 `free`，否则悬垂。
5. **异步生命周期是最容易出事的地方**：kernel 还在跑、cupy 数组已被 GC。要么 `stream.synchronize()`，要么持有引用。

## 建议

**主路径选 B（复用 cupy 指针）**，理由是收益/成本比压倒性：改动只是给每个 `.cu` 加一个 `*_dev` 导出（保留现有主机接口做回退），就能拿到 164x，而且不用自己造内存池——你现在的朴素实现之所以慢，恰恰就是 `cudaMalloc/cudaFree` + PCIe 拷贝各占一半。

**只有当出现「不装 cupy 也要用 GPU」这个需求时，才上 A**，并且到时候 A 也应该复用 B 的 `*_dev` 接口，只是把「谁来分配」换成自研内存池。

具体落地形态：
1. `code/cuda/cu/*.cu` 每个算子加 `launch_xxx_dev(..., void *stream)` 纯设备指针版本，现有 `launch_xxx` 保留。
2. EnNeuro 侧在 `device == 'cuda'` 时直接取 `Tensor.data.data.ptr` 分发到 `_dev` 算子；`device == 'cpu'` 走 numpy 老路。
3. 显存（包括融合算子的 workspace）全部交给 cupy 分配。
